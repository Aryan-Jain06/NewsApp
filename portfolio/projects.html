Project 01 — Python & TypeScript

Gramin Sahayak

A rural-India platform for government schemes, with misinformation detection running inline.

graminsahayak.in Source

Problem

Rural users cannot easily tell which scheme information is genuine. Policy data is scattered across sources, written in language that is hard to act on, and often unavailable in the reader's own language — which leaves a lot of room for misinformation.

Solution

A platform that gathers scheme data, verifies it, translates it, and checks claims for misinformation as they are read rather than in a later batch job — so the answer arrives while the user is still on the page.

Product features

  • Misinformation detection over an ensemble of five machine-learning models
  • Eligibility checker that works out which schemes apply to a user
  • Scheme detail pages and a bulletin board of current notices
  • Conversational assistant for questions in the user's own language
  • Guidance on where to physically go to apply
  • Multilingual onboarding and language selection

Architecture

Pipelines extract and verify policy data at source, then translate it. The five detection models sit behind an inference layer tuned for low-latency environments, so a claim is scored inside the request instead of offline. A React front end on Supabase serves the schemes, the assistant and the eligibility flow.

Technology

Python FastAPI ML ensemble Low-latency inference Gemini Sarvam AI React TypeScript Supabase

Results

Deployed and running at graminsahayak.in, serving scheme information in multiple Indian languages with misinformation checks returned inline.

Project 02 — Go

HookRelay

Webhook delivery as a standalone service, built so events are never silently lost.

Source

Problem

An application that sends its own webhooks loses events whenever a subscriber is down: the request fails, nothing retries it, and there is no record of what never arrived. Every team ends up rebuilding the same retry logic badly.

Solution

Move delivery into a service that takes responsibility for at-least-once delivery. Producers publish an event once; HookRelay persists it, fans it out to every subscribed endpoint, signs each delivery, retries failures for hours, and parks whatever is still failing somewhere it can be inspected and replayed.

Product features

  • HMAC-signed deliveries, with a per-endpoint secret that can be rotated
  • Eight retry attempts on an exponential backoff schedule
  • Dead-letter queue with per-delivery and bulk replay
  • Event timeline showing every attempt, status code and latency
  • Dashboard with success rate, deliveries per minute and p95 latency
  • Per-tenant API keys for publishing

Architecture

A producer POSTs an event; it is persisted in PostgreSQL and fanned out into one delivery per subscribed endpoint. Deliveries are queued on Redis Streams, and workers pull them, POST to the endpoint and record the attempt. Because the queue and the record of truth are separate, a worker dying mid-flight loses nothing — the delivery is still in the stream.

Technology

Go Redis Streams PostgreSQL Next.js Prometheus Docker Compose Caddy

Results

A load and chaos run fanned 10,000 events into 30,000 deliveries with zero lost, including a hard SIGKILL of the worker mid-delivery. The dashboard run recorded a 100% success rate at 251 ms p95.

Project 03 — Go

SeatSync

High-concurrency ticket booking where the same seat can never be sold twice.

Source

Problem

When hundreds of people go for the same seats at the same instant, both naive implementations fail: optimistic writes double-sell seats, and a global lock serialises every booking in the venue.

Solution

Split the problem across two stores. Redis holds the transient claim — a five-minute hold that expires by itself, so nothing has to remember to clean it up and a crashed server does not strand a seat. PostgreSQL holds the permanent sale, with a partial unique index that makes a second sale of the same seat impossible at the database level.

Product features

  • Live seat map, colour-coded by state, updating over WebSocket
  • Hold up to six seats at once, all-or-nothing
  • Five-minute hold with a live countdown to expiry
  • Idempotent payment step that is safe to retry
  • Expiry worker reconciling lapsed holds every two seconds

Architecture

A Next.js seat map talks REST to a Go API on chi and keeps a WebSocket open to a hub with one room per event. Services take Redis locks with SET NX EX through a Lua script, commit sales in PostgreSQL transactions, and broadcast every state change to the room. A background worker sweeps holds whose TTL has lapsed.

Technology

Go chi Redis PostgreSQL pgx WebSocket Next.js TypeScript

Results

An automated proof runs 500 concurrent booking attempts against 50 seats: exactly 50 confirmed, 450 rejected as clean conflicts, 0 unexpected outcomes, 427.9 ms p95 — then re-checked directly against the database.

Project 04 — Python

Sign Language Translator

Real-time sign language to text, running offline on ordinary hardware.

Source

Problem

Deaf and hard-of-hearing users have no convenient way to turn signs into text on the devices they already own, and the tools that exist tend to need a network round trip for every frame.

Solution

Recognise hand gestures from a plain webcam feed and classify them locally, assembling text as the user signs.

Product features

  • Live gesture recognition from a webcam feed
  • Indian and American Sign Language gesture sets
  • Desktop GUI with adjustable camera, gesture and output settings
  • Extensible to further sign languages

Architecture

MediaPipe extracts hand keypoints from each frame, a custom CNN classifies the gesture from those keypoints, and the result is assembled into text in the GUI. Training on keypoints rather than raw pixels is what keeps the model small enough to run locally.

Technology

Python TensorFlow MediaPipe CNN TinyML CustomTkinter

Results

Optimised with TinyML for edge deployment, giving offline, low-latency inference on resource-constrained hardware with no network dependency.

Project 05 — Python

Churn Prediction Model

Predicting which insurance agents are about to leave.

Source

Problem

Losing a productive insurance agent is expensive, and the warning signs are split across three separate record sets — agent activity, new business and renewals — so nobody sees them together in time.

Solution

Merge the three sources into one view per agent, engineer the behavioural signals that actually precede churn, and train a classifier to flag who is at risk.

Product features

  • Merges agent master, new-business and renewal datasets
  • Engineered features: renewal ratio, inactivity period, sales frequency
  • Compares logistic regression, random forest and XGBoost
  • Evaluation with confusion matrix and ROC curve

Architecture

A pipeline of preprocessing (nulls, encoding, outliers) → feature engineering across the merged datasets → model training and comparison → evaluation on held-out data.

Technology

Python XGBoost scikit-learn pandas

Results

94% accuracy with XGBoost, ahead of both logistic regression and random forest on the same features.

Project 06 — JavaScript

NewsFlash

A news reader that never makes you click 'next page'.

Source

Problem

Most news front-ends still paginate, so reading across a category means a reload and a lost scroll position on every page.

Solution

A single-page reader that appends the next batch as you reach the bottom, with categories as routes rather than reloads.

Product features

  • Live feeds across categories
  • Infinite scroll
  • Sticky navbar for switching category
  • Top-loading progress bar for request state
  • Responsive down to small phones

Architecture

A React single-page app that requests one page of articles per category and appends the next page when the reader nears the end, keeping fetch state in component state.

Technology

React JavaScript REST APIs Responsive CSS
